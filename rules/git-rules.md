# Правила Git-процесса проекта

Правила работы с Git в проекте: требования к рабочей ветке, формат сообщений коммитов и границы
безопасности git-операций. Цель — единообразное и машинно-проверяемое назначение изменений
и защита незафиксированной работы пользователя.

## Таблица правил

| ID | Правило |
|----|---------|
| GIT-005 | Ветка должна отражать одну законченную задачу или один логически связанный поток изменений |
| GIT-006 | Имена долгоживущих веток `main`, `master`, `develop` используются только как защищённые базовые ветки |
| GIT-009 | Сообщение коммита состоит из заголовка `{CODE}-NNN: описание задачи`, пустой строки и тела с перечнем выполненной работы |

| GIT-012 | В сообщения коммитов и описания PR/MR не добавляются служебные подписи об авторстве или генерации любых LLM-агентов и инструментов (`🤖 Generated with …`, `Co-Authored-By: <LLM-агент> …`) |
| GIT-015 | Коммит и push выполняются только по явному запросу пользователя |
| GIT-016 | Без явного запроса — подготовить изменения, показать состав коммита и предложенное сообщение, дождаться подтверждения |
| GIT-017 | Запрещены `push --force`, `git reset --hard`, `git checkout .` и другие деструктивные операции без явного разрешения пользователя |
| GIT-018 | Запрещено восстанавливать файлы через git (`git checkout HEAD -- …`, `git restore`, `git stash pop` и т.п.) без явного указания пользователя |
| GIT-019 | Запрещено читать историю git (`git log`, `git show`, `git blame` и т.п.) и сообщения коммитов без явного указания пользователя |
| GIT-020 | Гейт редактирования: перед изменением файла проверить наличие в нём незакоммиченных правок; при их наличии — сначала закоммитить их, затем вносить новые |
| GIT-021 | Машинный релизный коммит — созданный релизным сценарием репозитория, изменяющий только файл версии и озаглавленный `Релиз vX.Y.Z` — освобождается от требований `GIT-009` и `GIT-010` к коду и номеру задачи |

> Номер правила неизменен: ссылки вида `GIT-012` из других документов остаются действительными.

## Рабочая ветка

**[GIT-005]** Ветка описывает один поток изменений. Если в ветку попадают независимые задачи, их разделяют
на разные ветки до начала работы либо явно фиксируют общий объединяющий смысл.

**[GIT-006]** Имена `main`, `master`, `develop` используются только для защищённых базовых веток.
Рабочая ветка не должна называться одним из этих имён.

Конкретный шаблон имён рабочих веток задаётся проектом, использующим это окружение.

> **Примечание:** создание и слияние веток изменяют состояние репозитория и подчиняются
> [GIT-015..017](#коммиты-и-push): без явного запроса пользователя ветки не создаются и не вливаются.

## Формат сообщения коммита

**[GIT-009]** Сообщение коммита состоит из заголовка, пустой строки и тела:

```text
{CODE}-NNN: общее описание задачи

что было сделано
```

Где:

- `{CODE}` — код проекта или трекера задач заглавными латинскими буквами;
- `NNN` — трёхзначный номер задачи, только цифры от `000` до `999`;
- `общее описание задачи` — краткая формулировка задачи на русском языке;
- пустая строка отделяет заголовок от тела;
- `что было сделано` — тело коммита: перечень выполненной работы, одна или несколько строк.

Заголовок отвечает на вопрос «зачем» (задача), тело — на вопрос «что сделано» (работа в этом коммите).

Код проекта фиксируется один раз для репозитория и далее не меняется от коммита к коммиту.

Регулярное выражение для проверки заголовка (первой строки):

```regex
^[A-Z]{2,10}-[0-9]{3}: .+$
```

**[GIT-010]** Если код проекта, номер и описание задачи для коммита не указаны явно в запросе пользователя,
задаче, тикете или другом источнике работ, агент или разработчик обязан уточнить их до создания коммита.
Самостоятельно подставлять произвольный номер или выводить описание задачи «по смыслу», из контекста ветки
или из состава изменений запрещено.

Пример корректного сообщения:

```text
USP-009: изолировать профили аккаунтов Claude Code

Каталог аккаунта монтируется по CLAUDE_PROFILE, чужие профили скрыты анонимным томом.
Добавлена цель make claude-shell для входа в контейнер.
```

Примеры корректных заголовков:

```text
USP-001: добавить правила Git-процесса
USP-042: обновить состав образа Claude Code
USP-120: исправить ссылки на правила документации
```

Некорректные примеры:

```text
USP-1: добавить правило коммита
USP-000 добавить правило коммита
USP-000: 
docs: добавить правило коммита
Добавить правило коммита
```

Сообщение из одного заголовка без пустой строки и тела также некорректно: тело обязательно
по [GIT-009](#формат-сообщения-коммита).

## Проверка сообщения коммита

Перед созданием коммита агент или разработчик проверяет итоговое сообщение коммита.

Сообщение считается корректным, если одновременно выполняются условия:

1. Заголовок соответствует регулярному выражению из [GIT-009](#формат-сообщения-коммита).
2. Номер задачи состоит ровно из трёх цифр.
3. После двоеточия и пробела есть непустое описание задачи.
4. Заголовок отделён от тела пустой строкой, тело непустое и описывает выполненную работу.
5. Код, номер и описание задачи были явно получены из запроса, задачи, тикета или уточнены перед коммитом
   по [GIT-010](#формат-сообщения-коммита).

Если сообщение коммита не соответствует правилу, коммит не создаётся без явного решения пользователя
или ответственного разработчика.

Чек-лист применяется к коммитам, которые создаёт человек или агент. К машинному релизному коммиту он
не применяется — см. [GIT-021](#исключение-для-машинного-релизного-коммита).

## Исключение для машинного релизного коммита

**[GIT-021]** Коммит, созданный релизным сценарием репозитория, освобождается от требований
[GIT-009](#формат-сообщения-коммита) и [GIT-010](#формат-сообщения-коммита) к коду и номеру задачи.

Исключение действует только при одновременном выполнении трёх условий:

1. Автор коммита — релизный сценарий репозитория, а не человек и не агент.
2. Коммит изменяет ровно один файл — файл версии репозитория.
3. Заголовок имеет вид `Релиз vX.Y.Z`, где `X.Y.Z` — записанный в этом коммите номер версии.

Сообщение такого коммита состоит из заголовка, пустой строки и тела с прежним и новым номерами
версии — структура [GIT-009](#формат-сообщения-коммита) сохраняется, отсутствует только код задачи.

Основание исключения: релизный коммит не описывает задачу — он фиксирует единственную строку файла
версии, и решение о выпуске принимается запуском сценария, а не задачей трекера. Взять код и номер
задачи сценарию неоткуда: единственный ввод при запуске — разряд версии, а выводить их из контекста
запрещает [GIT-010](#формат-сообщения-коммита).

> **Внимание:** исключение ограничено релизным коммитом. Любой другой коммит, созданный
> автоматизацией, подчиняется [GIT-009](#формат-сообщения-коммита) и
> [GIT-010](#формат-сообщения-коммита) наравне с коммитом человека.

## Запрет служебных подписей

**[GIT-012]** В сообщения коммитов запрещено добавлять служебные подписи об авторстве или генерации,
проставляемые любыми LLM-агентами или инструментами разработки (Claude Code, Codex и любые другие ассистенты):

- строки вида `🤖 Generated with …` (например `🤖 Generated with Claude Code`);
- trailer-подписи соавторства-агента вида `Co-Authored-By: <LLM-агент> …` (например `Co-Authored-By: Claude …`).

Сообщение коммита содержит только формат `{CODE}-NNN: текст` по [GIT-009](#формат-сообщения-коммита).

В описания Pull Request (PR) и Merge Request (MR) запрещено добавлять подписи вида `🤖 Generated with …`.

Правило распространяется на любого LLM-агента и инструмент, а не только на Claude Code; запрет действует
независимо от формы и текста подписи.

## Коммиты и push

**[GIT-015]** Автоматические коммиты и push запрещены. Операция выполняется, только если пользователь явно:

- дал команду: «закоммить», «сделай коммит», «запушь», «commit», «push»;
- одобрил предложенный коммит в диалоге;
- дал разрешение через правила проекта или конфигурацию.

**[GIT-016]** Без явного запроса действует порядок по умолчанию:

1. Прочитать состояние рабочего дерева: `git status` и `git diff`.
2. Подготовить сообщение коммита по [GIT-009](#формат-сообщения-коммита).
3. Показать пользователю состав коммита и предложенное сообщение.
4. Дождаться явного подтверждения и только затем коммитить.

**[GIT-017]** Деструктивные операции запрещены без явного разрешения пользователя:

- `git push --force` и `git push --force-with-lease`;
- `git reset --hard`;
- `git checkout .` и любой массовый сброс рабочего дерева;
- удаление веток и перезапись опубликованной истории.

Обобщённое разрешение вида «делай как считаешь нужным» основанием не является: агент вправе отказать
и запросить явное подтверждение по конкретной операции.

> **Внимание:** деструктивные операции необратимы для незакоммиченной работы. Цена ошибки — потеря изменений,
> которые пользователь не успел зафиксировать.

## Восстановление файлов

**[GIT-018]** Запрещено восстанавливать файлы через git без явного указания пользователя. К восстановлению
относятся операции, меняющие рабочее дерево или индекс на основе истории либо спрятанных изменений:

- `git checkout HEAD -- <путь>` и `git checkout <commit> -- <путь>`;
- `git restore <путь>` и `git restore --staged <путь>`;
- `git stash pop` и `git stash apply`;
- отмена staged-удалений и любое возвращение удалённых или изменённых файлов.

Удалённые или изменённые файлы могут быть результатом намеренных действий пользователя. Самовольное
восстановление меняет состояние рабочего дерева вопреки его намерению, даже если выглядит логичным шагом задачи.

По умолчанию: описать обнаруженное состояние (что удалено, изменено, находится в индексе), предложить вариант
и дождаться явной команды. Принцип согласован с [GIT-017](#коммиты-и-push): git-операции, изменяющие рабочее
дерево или индекс, выполняются только по явному запросу.

## Чтение истории

**[GIT-019]** Запрещено читать историю git и сообщения коммитов без явного указания пользователя:

- `git log` в любом виде, включая `--oneline`, `-p`, `--stat`;
- `git show` и `git show HEAD`;
- `git blame` и `git annotate`;
- `git reflog`;
- любое чтение сообщения текущего или иного коммита.

История и сообщения коммитов — отдельный контекст, который пользователь может намеренно не вовлекать в задачу.
Самовольное обращение к ним привносит незапрошенные сведения и может направить работу по нежелательному пути.

По умолчанию агент опирается на текущее состояние рабочего дерева (`git status`, `git diff`) и на то,
что сообщил пользователь. Если для задачи действительно нужна история — запросить явное разрешение
и дождаться его.

> **Внимание:** ограничение затрагивает сверку с удалённой веткой и определение базы ответвления: без доступа
> к истории такие проверки выполняются по данным пользователя либо требуют явного разрешения на чтение истории.

## Гейт редактирования

**[GIT-020]** Перед каждым изменением существующего файла агент проходит гейт:

> **Есть ли в файле незакоммиченные правки?** — проверяется состояние файла: `git status -- <путь>`,
> `git diff -- <путь>` и staged-изменения `git diff --cached -- <путь>`.

Если незакоммиченные правки есть:

1. Новые правки поверх них не вносятся.
2. Сначала коммитятся существующие правки: код, номер и описание задачи подтверждаются
   по [GIT-010](#формат-сообщения-коммита), сообщение формируется по [GIT-009](#формат-сообщения-коммита).
3. Только после коммита вносятся новые правки.

Если файл чист — гейт пройден, редактирование выполняется сразу.

Незакоммиченные правки — отдельная, ещё не зафиксированная работа. Гейт не даёт смешать её с новыми изменениями:
без него откат новых правок затирает предыдущую работу, а коммит после редактирования склеивает в одном коммите
две разные задачи.

> **Примечание:** коммит по гейту — явное основание в смысле [GIT-015](#коммиты-и-push), поскольку разрешение
> задано правилом проекта. Требования [GIT-009](#формат-сообщения-коммита) и [GIT-010](#формат-сообщения-коммита)
> при этом сохраняются: без подтверждённых пользователем кода, номера и описания задачи коммит не выполняется —
> агент останавливается и запрашивает их.
