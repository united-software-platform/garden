## Язык и терминология

**[DOC-001]** Весь текст документации, комментарии в коде и текстовые ответы пишутся на **русском языке**.

**[DOC-002]** Идентификаторы кода — имена переменных, классов, методов, файлов — остаются на английском.

**[DOC-003]** Понятия без устоявшегося русского перевода не переводятся: Use Case, Value Object, Aggregate Root; названия инструментов: Doctrine, PHPUnit, Symfony.

---

## Структура файла

**[DOC-014]** Каждый файл открывается тремя обязательными элементами: заголовок, назначение (1–3 строки), секция навигации.

```markdown
# Название документа

Краткое назначение (1–3 строки).

---

## Навигация

- [Раздел 1](#раздел-1)
- [Раздел 2](#раздел-2)

---
```

**[DOC-012]** Уровни заголовков не пропускаются: строго `#` → `##` → `###` → `####`.

**[DOC-009]** Текст разбит на логичные короткие разделы — без "простыней" сплошного текста.

**[DOC-010]** Один раздел — один вопрос. Если раздел охватывает два вопроса, разделить его на два.

**[DOC-011]** Объёмные темы выносятся в отдельный файл; в основном документе — краткое резюме и ссылка "Подробнее".

**[DOC-013]** Маркированные списки — дефис `-`, нумерованные — `1.`. Вложенность не глубже двух уровней.

---

## Разметка Markdown

**[DOC-004]** Формат — CommonMark / GitHub-style Markdown, совместимый с GitLab и Obsidian. Нестандартные расширения не используются.

**Запрещено:**

- **[DOC-005]** HTML-теги: `<div>`, `<span>`, HTML-таблицы, `<h1>..<h6>`, `<a name="...">`
- **[DOC-006]** Wikilinks: `[[Note]]`
- **[DOC-007]** Четыре пробела в качестве отступа вместо fenced code blocks
- **[DOC-008]** Подчёркивание заголовков: `====` / `----`

## Элементы оформления

### Ссылки [DOC-015]

**[DOC-015]** Все ссылки — только относительные: `[текст](./path/file.md#anchor)`.

Запрещены: абсолютные URL на репозиторий, Wikilinks `[[...]]`, HTML-якоря `<a href="...">`.

**Исключение — `README.md` там, где цель ссылки действительно внешняя.** Критерий один: ресурс
лежит вне репозитория, и относительного пути к нему не существует. Так адресуются, например:

- **блок бейджей**, размещённый между заголовком файла и назначением: изображение запрашивается
  у внешнего сервиса (`shields.io`, `github.com/.../badge.svg`), а ссылка ведёт на внешний
  ресурс — пайплайн, реестр образов, страницу пакета;
- **названия пунктов перечня состава** — ссылка на проект инструмента, который в репозитории
  не лежит;
- **ссылка на репозиторий-источник** в тексте раздела — например на репозиторий базового образа,
  ведущий собственную инструкцию.

Перечень открыт: он показывает критерий, а не ограничивает исключение тремя местами.

Границы исключения:

- бейдж оформляется штатным Markdown `[![alt](url-изображения)](url-ссылки)`, обычная ссылка — `[название](url)`; HTML по [DOC-005](#разметка-markdown) остаётся запрещённым;
- ссылка на файл внутри репозитория (лицензия, `Dockerfile`, каталог правил) остаётся относительной;
- на прочие документы исключение не распространяется — там действует общее правило.

### Код [DOC-016]

**[DOC-016]** Код оформляется исключительно в fenced code blocks с обязательным указанием языка.

````markdown
```php
echo "Привет";
```

```bash
composer install
```
````

### Таблицы [DOC-017]

**[DOC-017]** Таблицы — стандартный Markdown `|...|`. HTML-таблицы запрещены.

### Диаграммы [DOC-018]

**[DOC-018]** Основной формат диаграмм — Mermaid. Для сложных архитектурных C4 — PlantUML в отдельных `.puml` файлах.

Требования к читаемости:
- Не более 7–10 узлов на одной диаграмме; при превышении — разбивать
- Связи подписаны: что передаётся, какой протокол
- Логические группы оформляются через `subgraph` (Mermaid) или `Boundary` (PlantUML)

### Callout-блоки [DOC-019]

**[DOC-019]** Выделение важной информации — через blockquote с текстовым маркером.

```markdown
> **Важно:** Критическая информация, которую нельзя пропустить.
> **Внимание:** Потенциальная проблема или ограничение.
> **Примечание:** Дополнительная информация для контекста.
```

**[DOC-020]** Ограничения, допущения, риски и неподдерживаемые сценарии фиксируются явно, а не подразумеваются.

## Жизненный цикл документа

**[DOC-022]** Каждый md-файл завершается таблицей версий:

```markdown
## Версионирование

| Версия | Дата | Задача | Агент | Модель | Описание изменений |
|--------|------|--------|-------|--------|--------------------|
| 1.0.0 | 2026-02-19 | Задача #4 | Claude Code | Claude 3.7 Sonnet | Начальное создание |
| 1.0.1 | 2026-02-25 | Задача #7 | Codex | GPT-5 | Добавлен раздел X |
```

Колонка `Задача` обязательна к заполнению и фиксирует причину изменения: номер задачи, тикет, запрос пользователя, решение ревью или другой конкретный источник, из которого пришло изменение. Значение `—` допустимо только для исторических записей, созданных до введения этого правила.

Колонка `Агент` обязательна к заполнению и фиксирует LLM-агента или инструмент, который внёс изменение.

Колонка `Модель` обязательна к заполнению и фиксирует модель LLM, использованную агентом при изменении.

Нумерация: `1.0.0` — первая версия; `1.0.1`, `1.0.2` — частичные изменения; `1.2.0` — кардинальная переработка.

**Исключение — `README.md`.** Файл с этим именем таблицу версий не ведёт: он адресован читателю
извне — пользователю проекта или набора, — и история правок документа для него шум. Источником
истории остаётся система контроля версий, а причина изменения фиксируется сообщением коммита
по [GIT-009](./git-rules.md#формат-сообщения-коммита).

Исключение задано типом документа, а не отдельным файлом: оно действует для любого `README.md`
репозитория. На прочие документы — правила, документы для контрибьюторов, описания инструментов —
оно не распространяется: их читатель ведёт сам репозиторий, и для него история правок документа
вместе с задачей, агентом и моделью — рабочая информация.

**[DOC-024]** Строки таблицы версий идут сверху вниз по возрастанию версии: первая запись истории — верхняя строка, актуальная версия — всегда последняя. Новая запись добавляется в конец таблицы, а не в начало.

Порядок «сверху вниз» делает актуальную версию предсказуемо последней строкой файла: её не нужно искать, и дописывание новой записи не сдвигает историю.

**[DOC-023]** При переносе контента в другой файл — исходный материал допустимо сжать, но ключевые факты и логика сохраняются. В файле-источнике остаётся ссылка на новое расположение.
