## Команды

| Команда | Что делает | Код возврата |
|---------|------------|--------------|
| `make model-build` | собирает дескриптор, печатает версию и хеш | `0` — успех, `1` — ошибка формата или валидации |
| `make model-diff` | показывает дельту против выпущенной версии, ничего не пишет | `0` — успех, `1` — ошибка процесса |
| `make model-gen` | выпускает версию: миграции, дескриптор, запись в реестр | `0` — выпущено или выпускать нечего, `1` — ошибка процесса |
| `make model-gen BASELINE=1` | выпускает свёртку модели целиком | то же |
| `make model-checks` | печатает запросы проверок целостности | `0` |
| `make model-verify DSN=...` | сверяет хранилище с моделью и прогоняет проверки | `0` — соответствует, `1` — есть расхождения |
| `make model-test` | прогоняет тесты инструментов | `0` — все прошли |
| `make db-up` | поднимает базу модели | `0` — поднята |
| `make db-apply` | применяет выпущенные миграции | `0` — применены |
| `make db-verify` | пересоздаёт базу и прогоняет все миграции с нуля | `0` — схема собралась |
| `make db-down` | останавливает базу и удаляет её данные | `0` |

Цели `db-*` требуют docker и выполняются на хосте. Агент вызывает их через раннер:

```bash
tools/host-runner/call.sh db-verify
```

Строка подключения к поднятой базе:

```text
из контейнера агента   postgresql://garden:garden@postgres:5432/garden
с хоста                postgresql://garden:garden@localhost:5432/garden
```

> **Внимание:** `db-down` и `db-verify` удаляют том базы. Это их назначение — сборка схемы
> с нуля, — но данные тестового хранилища теряются без подтверждения.

## Раскладка и именование

```text
changelog/
  master.yaml          порядок применения, генерируется
  registry.yaml        реестр выпусков, генерируется
  core/                общие элементы и замыкающие миграции
  br/                  миграции типа BR
  rel/                 сигнатуры связей
```

Каталог определяется элементом модели, который изменился, а не таблицами, которые трогает SQL.
Поэтому история одного типа лежит в одном каталоге за всё время его существования.

Имя файла — метка времени вида `Version20260915142233.sql`. Оно уникально без общего счётчика
и не конфликтует при слиянии веток.

> **Внимание:** порядок применения именами файлов **не** задаётся — хронология выпуска не
> совпадает с зависимостями элементов. Порядок задаёт `master.yaml` явными включениями:
> сначала общие элементы, затем типы узлов, затем связи.

## Замыкающая миграция

Каждая версия завершается замыкающей миграцией. Она записывает номер версии и хеш модели
и несёт предусловие: в хранилище лежит хеш предыдущей версии.

```sql
--changeset model-gen:close.1.3.0 labels:model-1.3.0
--comment: 1.2.0 -> 1.3.0
--preconditions onFail:HALT
--precondition-sql-check expectedResult:1 SELECT count(*) FROM model_state WHERE hash = 'sha256:aaa…'
UPDATE model_state SET version = '1.3.0', hash = 'sha256:bbb…';
```

Отсюда три свойства: отпечаток обновляется той же транзакцией, что и схема; накат на неожиданное
состояние останавливается до выполнения изменений схемы; версия, не менявшая схему, всё равно
видна в истории.

## Неизменяемость выпущенного

Выпущенный файл не меняется ни по имени, ни по содержанию: путь входит в опознание changeset'а,
а содержание — в контрольную сумму реестра. Исправление выпускается следующей миграцией.

`make model-verify` сверяет контрольные суммы и сообщает об изменённом или удалённом файле.

## Смена СУБД

Новое хранилище получает не историю, а свёртку модели:

```bash
make model-gen BASELINE=1
```

Переигрывать историю на новом движке не нужно: миграции описывают путь, а результат целиком
выводится из дескриптора. Перенос данных — отдельная задача, к контракту модели не относящаяся.
