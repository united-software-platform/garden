# Устройство проверок качества кода

## Context

Мотивация — в [proposal.md](./proposal.md), требования — в [code-quality](./specs/code-quality/spec.md) и [ci-checks](./specs/ci-checks/spec.md).

Состояние, которое задаёт рамки решения:

- Python 3.12, менеджер окружения — `uv`; зависимости объявлены в `pyproject.toml`, тестовые — в необязательной группе `dev`.
- Код: пакет `tools/garden_model` (16 модулей), `tests` (9 файлов, 116 функций), отдельный скрипт `tools/host-runner/runner.py`. Всего около 3500 строк.
- Пакет лежит в `tools/`, а не в корне: и `pytest`, и вызовы из `Makefile` добавляют путь через `pythonpath`/`PYTHONPATH`. Любой инструмент, разрешающий импорты, обязан знать про этот корень.
- Код типизирован почти везде: аннотации стоят в сигнатурах модулей пакета, тестовые функции не аннотированы вовсе.
- Комментарии и docstring'и — русские и длинные: 341 строка длиннее 100 символов, 183 — длиннее 120.
- Действующий пайплайн `model.yml` выполняет два не связанных между собой дела: гейт выпуска модели и прогон тестов.
- Выпущенные миграции в `changelog/` неизменяемы по требованию «Применённая миграция неизменяема» изменения `add-model-contract`.

## Goals / Non-Goals

**Goals:**

- Одна конфигурация проверок для локального прогона и пайплайна, один способ запуска — цель `Makefile`.
- Норма, действующая на весь код сразу, без базы накопленных нарушений.
- Пайплайны, разделённые по ответственности, с независимыми статусами.

**Non-Goals:**

- Проверка не-Python артефактов: YAML пайплайнов, `Makefile`, SQL, Markdown.
- Измерение покрытия тестами, аудит зависимостей, pre-commit hook'и.
- Матрица версий Python: проект объявляет `>=3.12` и проверяется на 3.12.

## Decisions

### Ruff как форматтер и линтер

Ruff закрывает обе роли: `ruff format` — аналог php-cs-fixer, `ruff check` — аналог связки flake8 с плагинами и isort. Один инструмент, одна конфигурация, один кэш, прогон на этом объёме кода — доли секунды.

Альтернатива — black + isort + flake8: три инструмента, три конфигурации и разбирательства, кто из них прав, когда их нормы расходятся. Отвергнута как более дорогая при том же результате.

Набор правил: `E`, `W`, `F` (базовые), `I` (порядок импортов), `N` (имена), `UP` (устаревшие конструкции), `B` (типовые ловушки), `C4`, `SIM`, `RET`, `RUF`. Правила документирования (`D`) не включаются: docstring'и в проекте пишутся по правилу [DOC-001](../../../rules/documentation-rules.md#язык-и-терминология) на русском и в форматы pydocstyle не укладываются.

Из набора отключены `RUF001`, `RUF002` и `RUF003` — поиск кириллических букв, похожих на латинские. Правила рассчитаны на код, где текст латинский, а кириллица в нём случайна; здесь наоборот — весь текст русский по [DOC-001](../../../rules/documentation-rules.md#язык-и-терминология), и на первом же прогоне они дали 98 находок на словах «строка», «схема», «удаление». Отключение записано конфигурацией, то есть решением ревью, а не пометками в коде — как того требует правило подавления в [code-quality](./specs/code-quality/spec.md).

### Длина строки — 100 символов

`line-length = 100` и включённое `E501`. Значение выбрано по факту: так уже оформлены комментарии в `Makefile` и текст документов, а 341 строка сверх нормы — накопленное расхождение, а не стиль.

Форматтер переносит код, но не переносит комментарии, docstring'и и строковые литералы — их перенос выполняется вручную. Это основной объём ручной работы в изменении.

Альтернатива — `line-length = 120`: дешевле на 158 строк, но оставляет в коде строки, которые не помещаются в окно ревью рядом с диффом. Отвергнута: цена разовая, а норма остаётся навсегда.

### mypy в режиме strict, с одним послаблением для тестов

`strict = true` для всего кода. Послабление ровно одно и записано секцией переопределения для `tests.*`: `disallow_untyped_defs = false` и `disallow_incomplete_defs = false`. Причина — фикстуры pytest подставляются по имени параметра, и аннотация 116 тестовых функций дала бы шум, не обнаружив дефектов. Остальные строгие настройки на тесты действуют: несовместимое присваивание и обращение к неизвестному атрибуту в тесте остаются ошибкой.

Альтернатива — исключить `tests` из проверки целиком: отвергнута, тесты вызывают тот же публичный интерфейс, что и потребители, и проверка типов ловит там расхождения раньше прогона.

Вместе с требованием аннотировать сигнатуры для тестов снимается и `disallow_untyped_calls`: иначе снятое требование вернулось бы через вызовы — каждый вызов неаннотированного тестового помощника считался бы ошибкой (на первом прогоне таких было 100 из 147).

Разрешение импортов: `mypy_path = ["tools"]` и `explicit_package_bases = true` — корень пакета тот же, что у `pytest`. Для `pgserver`, не поставляющего аннотаций, добавляется `ignore_missing_imports` точечной секцией переопределения; для `PyYAML` в dev-зависимости добавляется пакет аннотаций `types-PyYAML`.

Разбор YAML возвращает `Any`, и strict потребует явных сужений в `model.py`. Это ожидаемая работа, а не повод ослаблять режим: сужение на границе разбора — то самое место, где ошибка формата должна превращаться в `ModelError`.

### Три пайплайна вместо одного

- `tests.yml` — прогон `pytest`, включая тесты с временным PostgreSQL.
- `quality.yml` — три шага: `ruff format --check`, `ruff check`, `mypy`. Шаги раздельные, чтобы по логу было видно, какая именно проверка отказала.
- `model.yml` — остаётся только гейт выпуска модели; шаг тестов из него удаляется.

Раздельные файлы дают раздельные статусы в предложении изменений и прямо выражают требование «Проверки разделены по ответственности». Альтернатива — один файл с тремя job'ами: общий кэш, но общий же статус и смешанная ответственность; отвергнута.

Шаги качества выполняются последовательно в одном job'е и не прерываются на первом отказе (`continue-on-error` не используется, применяется `if: always()` на последующих шагах): автор видит все находки за один прогон, а не по одной за push.

### Запуск — через uv, тем же способом, что в Makefile

Пайплайн и локальная цель вызывают инструмент одинаково: `uv run --extra dev <инструмент>`. Версии `ruff`, `mypy` и `types-PyYAML` закрепляются в группе `dev` точным указанием (`==`), а не нижней границей — иначе вердикт на неизменном коде менялся бы вместе с выходом новой версии инструмента.

### Цели Makefile

Добавляются `format` (правка на месте), `lint`, `typecheck` и `check`. `check` — точка входа: вызывает три под-цели рецептом через `$(MAKE)`, как того требует [MAKE-003](../../../rules/makefile-rules.md#под-цели-после-дробления-make-003). Каждая секция укладывается в норму [MAKE-001](../../../rules/makefile-rules.md#норма-объёма-секции-make-001) — 30 строк.

Цель `model-test` остаётся как есть: она уже прогоняет тесты и ничего в связи с разделением пайплайнов не меняет.

### Порядок приведения кода к норме

Правка выполняется в порядке, при котором каждый шаг проверяем: конфигурация → форматтер → находки линтера → ошибки типов. Обратный порядок заставил бы переделывать ручные правки после прогона форматтера.

Тесты прогоняются после каждого шага: форматирование и правки ради линтера не должны менять поведение, и единственное доказательство этому — зелёный прогон.

## Risks / Trade-offs

- **Правка всех файлов конфликтует с незавершёнными ветками** → изменение выполняется отдельными коммитами по шагам, форматирование — отдельным коммитом; конфликт в нём разрешается повторным прогоном форматтера, а не разбором смысла.
- **strict на разборе YAML потребует заметной правки `model.py`** → сужения ставятся на границе разбора, где уже возбуждается `ModelError`; если объём окажется больше ожидаемого, работа остаётся внутри одной задачи и не растекается по остальным модулям.
- **Тестовые функции названы по-русски** → правила `N` проверяют регистр, а не алфавит, и кириллические имена им не противоречат; риск снимается прогоном линтера на шаге конфигурации, до массовой правки.
- **`pgserver` без аннотаций** → точечное `ignore_missing_imports` для одного модуля вместо глобального ослабления.
- **Перенос длинных комментариев вручную рискует исказить текст** → переносятся только строки, содержание не переписывается; смысловая правка комментариев в это изменение не входит.
- **Два пайплайна вместо одного ставят окружение дважды** → принятая цена: время прогона растёт, зато отказ читается по статусу без захода в лог.

## Migration Plan

1. Конфигурация и зависимости: секции `[tool.ruff]`, `[tool.mypy]`, dev-зависимости с закреплёнными версиями. Прогон инструментов в режиме отчёта — фиксируется исходный объём находок.
2. Форматирование всего кода одним прогоном, отдельным коммитом. Проверка: `pytest` зелёный.
3. Находки линтера: автоисправимые — прогоном с `--fix`, остальные — вручную. Проверка: `ruff check` без находок, `pytest` зелёный.
4. Ошибки типов: аннотации и сужения. Проверка: `mypy` без ошибок, `pytest` зелёный.
5. Пайплайны: `tests.yml`, `quality.yml`, удаление шага тестов из `model.yml`.
6. Цели `Makefile` и документация порядка проверок.

Откат: изменение не трогает ни данные, ни выпущенные миграции, ни интерфейс инструментов — откатывается снятием коммитов. Единственное необратимое последствие — переформатированная история строк в `git blame`.

## Open Questions

- Нужно ли проверять качество кода самих пайплайнов и `Makefile` (например, `actionlint`) — вопрос отдельного изменения: на состав и настройку проверок Python он не влияет.
