# Проверки качества кода и тесты в пайплайне

## Why

В репозитории около 3500 строк Python — пакет инструментов модели `tools/garden_model`, 26 файлов тестов и раннер хоста, — но автоматически проверяется из них только прогон `pytest`, и тот выполняется шагом внутри пайплайна контракта модели. Ни оформление кода, ни статический анализ не проверяет ничто: единообразие отступов, порядок импортов, неиспользуемые имена и ошибки типов ловит только ревью, то есть человек и не всегда.

Проекту нужен тот же порядок, что в PHP-проектах даёт связка php-cs-fixer и phpstan: машинная норма оформления, статический анализ и блокирующая проверка в пайплайне на каждом изменении.

## What Changes

- Подключается **Ruff** — форматтер (аналог php-cs-fixer) и линтер: единая норма оформления, порядок импортов, неиспользуемые имена и импорты, типовые дефекты.
- Подключается **mypy в режиме `strict`** — аналог phpstan максимального уровня: проверка типов всего Python-кода репозитория.
- Конфигурация обоих инструментов живёт в `pyproject.toml` — один источник для локального прогона и пайплайна; версии инструментов закрепляются в dev-зависимостях.
- Пайплайны разделяются по ответственности: **`tests.yml`** прогоняет тесты, **`quality.yml`** — форматирование, линтер и проверку типов. Шаг тестов уходит из `model.yml`: в нём остаётся гейт выпуска модели.
- Появляются цели `Makefile`: `format` (правка), `lint`, `typecheck` и `check` (весь набор проверок разом) — вердикт локального прогона совпадает с вердиктом пайплайна.
- Существующий код **приводится к норме целиком в рамках этого изменения**: форматирование всех файлов, устранение всех находок линтера и типизатора. Диф крупный и намеренно не смешивается с содержательными изменениями.
- Под проверку попадает весь Python репозитория: `tools/garden_model`, `tests`, `tools/host-runner/runner.py`.

## Capabilities

### New Capabilities

- `code-quality`: норма оформления Python-кода и её машинная проверка — форматтер, линтер, проверка типов, единая конфигурация, совпадение локального вердикта с вердиктом пайплайна.
- `ci-checks`: состав автоматических проверок репозитория — разделение по пайплайнам, блокирование слияния, воспроизводимость каждой проверки одной целью `Makefile`.

### Modified Capabilities

Нет: в `openspec/specs/` зафиксированных capability пока нет, а требования к пайплайну не заданы ни одной из них — существующий `model.yml` описан только изменением `add-model-contract` на уровне работ.

## Impact

- **Новые файлы:** `.github/workflows/tests.yml`, `.github/workflows/quality.yml`.
- **Изменяемые файлы:** `.github/workflows/model.yml` (шаг тестов удаляется), `pyproject.toml` (секции `[tool.ruff]`, `[tool.mypy]`, dev-зависимости), `Makefile` (четыре цели), весь Python-код репозитория — переформатирование и устранение находок.
- **Зависимости:** `ruff` и `mypy` добавляются в необязательную группу `dev` с закреплёнными версиями; обновление инструмента становится осознанным изменением, а не внезапно красным пайплайном.
- **Объём массовой правки:** 26 файлов переформатируются; около 340 строк длиннее 100 символов, из них ~34 — комментарии и заметная часть — строковые литералы и docstring'и: форматтер их не переносит, перенос выполняется вручную.
- **Допущение:** `strict` требует аннотаций каждой функции; для тестов требование аннотаций сигнатур снимается (`disallow_untyped_defs = false`) — фикстуры pytest подставляются по имени, и аннотация 116 тестовых функций дала бы шум без находок. Остальные строгие настройки действуют и на тесты.
- **Ограничение:** проверяется только Python. YAML пайплайнов, `Makefile`, SQL выпущенных миграций и Markdown документации остаются вне проверки; для `Makefile` норма объёма уже задана [MAKE-001](../../../rules/makefile-rules.md#норма-объёма-секции-make-001) и своей проверкой.
- **Ограничение:** выпущенные миграции в `changelog/` неизменяемы — под форматирование и линтер они не попадают ни при каких настройках.
- **Вне объёма:** измерение покрытия тестами, проверки безопасности зависимостей, pre-commit hook'и, матрица версий Python — репозиторий фиксирует Python 3.12 и проверяется на нём.
- **Риск:** одновременная правка всех файлов конфликтует с любой незавершённой веткой. Изменение выполняется отдельным коммитом, не смешанным с содержательными правками, чтобы конфликт разрешался переформатированием, а не разбором смысла.
