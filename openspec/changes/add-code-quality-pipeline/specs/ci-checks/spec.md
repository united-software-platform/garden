# Автоматические проверки репозитория

## Purpose

Задаёт состав автоматических проверок изменений репозитория, их разделение по ответственности, условия блокирования слияния и требование воспроизводить любую проверку локально одной командой.

## ADDED Requirements

### Requirement: Каждое изменение проходит проверки

Проверки репозитория SHALL выполняться автоматически для каждого предложенного изменения и для состояния защищённой ветки. Запуск проверки вручную MUST NOT быть условием её выполнения.

#### Scenario: Открыто предложение изменений

- **WHEN** открыто или обновлено предложение изменений
- **THEN** запускаются все проверки репозитория
- **AND** их вердикты видны в предложении до слияния

### Requirement: Проверки разделены по ответственности

Каждая проверка SHALL принадлежать ровно одному пайплайну: тесты, качество кода и гейт выпуска модели SHALL быть разделены. Одна и та же проверка MUST NOT выполняться в двух пайплайнах.

#### Scenario: Тесты прогоняются один раз

- **WHEN** изменение затрагивает и код инструментов, и модель
- **THEN** тесты прогоняются пайплайном тестов
- **AND** пайплайн гейта модели их не повторяет

#### Scenario: Причина отказа видна по статусу

- **WHEN** проверка качества кода не пройдена, а тесты пройдены
- **THEN** статус пайплайна качества кода красный, статус пайплайна тестов зелёный

### Requirement: Непройденная проверка блокирует слияние

Провал любой проверки репозитория SHALL останавливать слияние изменения. Проверка, вердикт которой носит справочный характер, SHALL быть помечена как неблокирующая явно.

#### Scenario: Найдено нарушение нормы оформления

- **WHEN** проверка качества кода завершается ненулевым кодом возврата
- **THEN** изменение не может быть слито
- **AND** в выводе названы файлы и правила, вызвавшие отказ

### Requirement: Проверка воспроизводима локально

Каждая проверка SHALL запускаться локально одной командой репозитория. Вердикт локального прогона и вердикт пайплайна на одном и том же состоянии рабочего дерева SHALL совпадать.

#### Scenario: Автор проверяет изменение до отправки

- **WHEN** автор запускает набор проверок локально и получает успех
- **THEN** пайплайн на том же состоянии кода даёт успех

#### Scenario: Расхождение вердиктов

- **WHEN** локальный прогон и пайплайн расходятся в вердикте на одном состоянии кода
- **THEN** расхождение считается дефектом конфигурации проверок

### Requirement: Тесты прогоняются полностью

Пайплайн тестов SHALL выполнять весь набор тестов, включая тесты, поднимающие временное хранилище. Сокращение набора ради времени прогона MUST NOT применяться.

#### Scenario: Тест требует хранилища

- **WHEN** тест поднимает временный экземпляр СУБД
- **THEN** пайплайн выполняет его наравне с остальными
- **AND** отказ такого теста блокирует слияние

### Requirement: Окружение проверок детерминировано

Пайплайн SHALL устанавливать зависимости из описания проекта с закреплёнными версиями инструментов и SHALL использовать ту же версию языка, что объявлена проектом.

#### Scenario: Версия языка объявлена проектом

- **WHEN** проект объявляет требуемую версию языка
- **THEN** пайплайн выполняет проверки на этой версии
